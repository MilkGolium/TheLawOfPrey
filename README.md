# The Law Of Prey

## 项目简介
另类的古生物冒险游戏。

## 开发者分工情况
当前人数 2 人，按照首字母排序。

### Liling
#### 定位
Game Designer (GD)

#### 职责
主策划的核心职责是定义游戏“最终做成什么样”，并带领设计团队把抽象的想法变成好玩、可赚钱、能落地的产品。

##### 游戏灵魂与核心体验的定义

GD 必须清楚地知道这款游戏到底是个什么东西、卖点在哪里、好玩在哪里。

##### 确立核心玩法闭环
- 定义最基础的玩家行为循环。例如《大鱼吃小鱼》：“吃东西 => 会变大 => 解锁新海域 => 会杀更强的敌人 => 继续吃”。
- 这个闭环必须极其清晰、可验证，而不是拍脑门说“我们要借鉴 Minecraft 和塞尔达”。

##### 把握游戏体验的方向盘
- 控制游戏的基调与风格，例如画风倾向、叙事氛围、玩家情感体验。
- 当团队内部对某个玩法设计产生分歧时，GD 必须根据游戏的核心定位做出取舍：“这个玩法虽然挺有意思，但偏离了我们的核心主题，砍掉。”

##### 体系化系统设计与架构搭建

GD 不能只凭感觉“想点子”，必须精通如何将一个巨大的游戏世界拆解为互相关联的子系统。

1. 设计模块拆解：
把抽象的游戏拆分为具体的框架：战斗系统、成长与数值系统、关卡/地图设计、经济与背包系统、UI/UX 交互逻辑、剧情与任务系统。

2. 制定规范与标准：
- 制定团队的 GDD（游戏设计文档）规范、数据表配置标准。
- 确保下面的普通策划（系统策划、数值策划、关卡策划）写出来的文档逻辑严密，符合程序和美术的接入标准。

##### 数值模型与商业化设计

游戏不仅要“好玩”，还要“耐玩”，甚至要“能盈利”。

1. 数值与成长体验：
- 统筹玩家的成长曲线（例如等级、装备属性、怪物血量成长、技能伤害加成）。
- 控制游戏节奏：什么时候给玩家正反馈，什么时候给玩家制造挫败感再提供突破感。


2. 经济系统与资源循环：
算清产出与消耗平衡（比如：玩家做完主线得 100 金币，买一把剑要 80 金币，强化要 50 金币，如何制造合理的资源缺口）。

##### 跨部门对齐与“需求翻译”

这是区分“口嗨策划”和“合格主策划”的分水岭。GD 必须把设计语言翻译成**技术语言**和**美术语言**。

1. 对齐技术总监（TD）：
- 在提出玩法前，先与 TD 进行技术评审。
- GD 必须理解技术边界，不能提出“让手机同时渲染 10 万个带物理效果的 NPC”这种反技术的荒谬需求。


2. 对齐美术指导：
把玩法需求转化为可视化的美术需求列表（例如：“我们需要 5 种不同属性攻击的打击特效，要求剪影清晰、不妨碍玩家看清 Boss 动作”）。

##### 游戏调优与“好玩度”验收

1. 打击感与反馈调试
负责游戏最细微体验的调优：受击停顿（Hitstop）、屏幕震动（Screen Shake）、音效配合、UI 动画弹窗节奏。这些往往是决定游戏是“干瘪”还是“爽快”的关键。


2. 玩法测试与数据迭代：
组织内部和外部玩家测试，观察玩家在哪个关卡卡住、在哪个环节流失，根据真实的反馈数据去修改设计方案。

##### 策划团队管理与产出把控

1. 任务拆解与进度追查：
把大的游戏目标拆解成具体的小卡片分配给执行策划，规定明确的 DoD（交付标准）和 Deadline。

2. 质量审核（Review）：
审核下属策划提交的表格、Markdown 规则案，把有逻辑漏洞、不可立项的需求当场打回，绝不把垃圾需求丢给程序员。

### Voosk
#### 定位
Technical Director (TD)

#### 职责
##### 技术选型与底层架构设计
- 引擎、工具选型：评估项目需求、性能上限、跨平台部署难度、团队学习成本、社区生态。
- 核心底层架构搭建：
    - 设计高可用、低耦合的架构，如 ECS 架构、状态机、事件总线/消息队列、数据持久化与存档系统。
    - 制定数据结构与接口标准，如保证策划的 CSV/JSON 数据可以无缝读入并正确解析。
- 技术攻坚（R&D）：解决项目难度最大，最硬核的技术卡点。

##### 团队协作规范与工作流程搭建
- 代码与版本控制规范
    - 搭建并维护 Git/SVN/Perforce 仓库。
    - 制定分支管理策略，例如 Git Flow: Main/Develop/Feature 分支命名与合并规范。
    - 编写代码规范（Code Style Guides），统一命名规则、注释要求与目录结构。
- 资源与管线（Pipeline）规范
    - 明确美术资源导出标准（模型面数要求、贴图纹理格式、分辨率上限、动画骨骼节点规范）。
    - 明确策划的数据配置表（CSV/Excel/Numbers）的校验机制，检查是否填错数据导致游戏崩溃或者出错。

##### 技术赋能、降低非技术人员门槛
- 关卡、剧情编辑器开发：例如节点式对话编辑器、触发器可视化面板，让策划不需要写代码即可刷地图、配置任务逻辑。
- 自动化构建与 CI/CD 流程：
    - 搭建自动化打包流水线（例如 Github Actions）。
    - 做到“代码一合并，自动编译生成 PC/Mac 测试包”，节省人工打包时间。

##### 性能优化与技术质量把控
- 性能指标监控：监控游戏过程中的 CPU/GPU 占用、内存泄露（Memory Leak）、DrawCall（绘制调用数）、帧率（FPS）表现。
- 代码审查（Code Review）：审查其他程序员提交的代码，把控逻辑严密性，杜绝低效循环、内存溢出以及其他潜在的逻辑问题。
- 自动化测试与 Crash 监控：接入日志捕获与崩溃分析工具，快速定位和修复上线或者测试阶段的致命崩溃（Crash）。

##### 沟通对话与需求翻译
- 技术可行性评估（Technical Feasibility Review）：当策划提出一个天马行空的想法（例如我想让一万个 NPC 在地图上自由 AI 打架）的时候，TD 需要评估性能成本与开发工时，告知策划是否可行，是否有替代方案。
- 需求拆解与工时排期：把策划整理好的文字需求翻译成具体的任务卡片（Task/JIRA），精确评估工时（例如背包系统需求，拆解为数据结构设计2Hours，UI 绑定 3Hours，存档序列化 2Hours）。

##### 团队搭建与人才梯队建设
- 招纳贤士技术把关：负责招募合格的程序员/技术美术（TA），识别出只会增删查改没有过硬本领的人员。
